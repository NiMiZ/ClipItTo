# Password-field copies: what each platform offers (roadmap 19)

Question: some browsers and apps set no password-manager marker when a password is copied (a field's reveal-and-copy,
an extension's "copy password" button, a "suggest password" box). Is there a reliable, cheap and safe signal that a copy
came from a password field, without reading more of the clipboard than now and without screen scraping?

Research date 2026-11. Sources are public documentation and bug trackers; nothing here was measured on a real
Windows or macOS machine (this was done on Linux), so every "reported" below is a claim to verify, not a test result.

## Summary

| Signal | Platform | Reliable | Cheap | Safe | Decision |
|---|---|---|---|---|---|
| Marker formats / types set by the copying app | all | Yes, when the app sets one | Yes (names only) | Yes | **Done** (extended list) |
| Copy owner process | Windows | Only tells the app, not the field | Yes | Yes | Not a signal by itself (a browser owns every copy) |
| UI Automation `IsPassword` of the focused element | Windows | No (see below) | No | Mixed | **Not implemented** |
| `IsSecureEventInputEnabled()` | macOS | No (global flag) | Yes | Yes | **Not implemented** |
| `x-kde-passwordManagerHint` | Linux | Yes, when the app sets one | Yes | Yes | Already handled |

## Windows

- Documented by Microsoft for clipboard history and cloud clipboard: `ExcludeClipboardContentFromMonitorProcessing` (any
  value), `CanIncludeInClipboardHistory` and `CanUploadToCloudClipboard` (DWORD 0). Password managers (Bitwarden,
  KeePass, 1Password) set them; KeePass also sets `Clipboard Viewer Ignore`. ClipItTo already honours all four.
- A browser copying from a password field: browsers refuse to copy the masked value of `<input type="password">`
  (Firefox has a test, `test_cut_copy_password.html`, that the raw value is not put on the clipboard; older reports say
  nothing is copied). So the leak is not "Ctrl+C in a masked field" but values that reach the clipboard another way: the
  field after "show password" (then it is a plain text input), a page's own copy button, a browser extension's "copy
  password" action (a 1Password community thread reports extension copies not marked as concealed). I found no source
  saying Chrome, Edge or Firefox add any marker format for these. Treat them as unmarked.
- UI Automation `IsPassword` (`UIA_IsPasswordPropertyId`) on the focused element: Microsoft defines it as "the content
  is protected". Whether Chromium and Firefox expose it for `type=password` inputs I could not confirm from
  documentation; Chromium builds its accessibility tree (and UIA provider) only after a client asks, so the first
  query would switch accessibility on in every browser (a measurable slowdown and a visible side effect). The query is a
  cross-process COM call that can block on a hung app, needs COM initialised on the thread, and answers for the
  focus **now**, not at copy time (the clipboard event arrives after the copy; the user may have moved on). The case it
  would catch (a revealed password) is no longer a password field. Not reliable, not cheap, cannot be tested here.
  **Not implemented.**

## macOS

- nspasteboard.org conventions (community, not Apple's): `org.nspasteboard.ConcealedType` (confidential: 1Password,
  KeePassXC, Bitwarden desktop), `org.nspasteboard.TransientType` (restored within seconds: do not record),
  `org.nspasteboard.AutoGeneratedType` (made by a program, not the user). Apple's Tahoe clipboard history is reported to
  hide items with these types.
- Meaning for ClipItTo: Concealed is a secret and follows the password flow (sealed, or skipped). Transient and
  AutoGenerated are not secrets by definition: they are skipped and never sealed (a deliberate choice that already
  existed). Extra types clipboard managers such as Maccy ignore: `net.antelle.keeweb` (KeeWeb, treated as a secret),
  `de.petermaurer.TransientPasteboardType`, `com.typeit4me.clipping`, `Pasteboard generator type` (treated as
  transient).
- `IsSecureEventInputEnabled()` is true while any process holds secure event input: a focused password field
  (`NSSecureTextField`, and web password fields in Safari/Chrome), but also Terminal/iTerm2 "Secure Keyboard Entry"
  (often on permanently), password-manager unlock sheets and a process that crashed without releasing it. It is a system-wide
  boolean with no owner and no field. ClipItTo polls `changeCount`, so the answer would also be for the poll time, not the
  copy. In a password field the copy is normally refused anyway. Result: many false positives (silently hiding normal
  copies for users with Secure Keyboard Entry), few true ones. **Not implemented.**

## Linux

- `x-kde-passwordManagerHint` (value `secret`): KeePassXC, Bitwarden, KDE tools. Already honoured on X11, wlroots/KDE
  Wayland and by the GNOME extension. No browser sets it for a password field.
- X11 and Wayland have no focus-based password-field signal that works across toolkits (AT-SPI exposes a
  `PASSWORD_TEXT` role, but needs the accessibility bus and has the same timing problem). Not pursued.

## Conclusion

The only reliable signal is a marker set by the copying app, so the work is to know every marker in use. This change adds
KeeWeb (secret) and three transient pasteboard types, with tests. Focus-based detection (`detect_password_fields`) is left
out: neither candidate is reliable at copy time, and shipping an untestable guess that hides copies is worse than the
existing rules (`detect_passwords`, `detect_secrets`, own rules, *Not a password*). Revisit if a real Windows/macOS test
shows a browser exposing a field signal that is reliable at copy time.
